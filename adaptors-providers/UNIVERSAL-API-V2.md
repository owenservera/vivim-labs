## 1. Five independent identities
1. Target ID VIV-0001..VIV-1000: research inventory, never executable.
2. Semantic operation ID (HQ name@version, e.g. vivim.message.list@1): common meaning, schema and risk.
3. Provider binding: operation + product + adapter version + source/evidence revision. Multiple bindings can implement the same meaning.
4. Account/source identity: opaque Host-resolved accountRef, workspace and active grant; no secrets or account inference from a display label.
5. Execution identity: existing Host planId, planDigest, semantic/effect digest, journal claim and receipt. An observation/event identity is independent of an execution ID.
Studio primitives are private implementation details; no arbitrary evaluate, shell, CDP, cookie or storage access in public tool surfaces.

## 2. Capability descriptor (proposed derived view, not a new persisted catalog)
A capability has semanticId, existing actionId (or null), operation version, family, inputSchema and outputSchema IDs, effect/risk, source anchors, binding references, readiness and contract revision. A binding carries targetId, provider/product, transport, adapter revision, supported fields/operations, constraints and evidence. An account-specific projection adds accountRef, grant status, scope, freshness and permitted actions. Separate lifecycle axes: inventory/research; schema/mapping; source-wired/live-verified; account connection; action authorization. No single available boolean replaces those axes.
Example operation vivim.message.list@1 is a proposed semantic ID, not a registered capability; do not claim Gmail or WhatsApp support merely because mapped. Retain provider-specific fields as namespaced typed extensions; absent data stays unknown, not false. Use existing HQ registry governance and source projections. Never trust client-supplied risk/readiness or scope.

## 3. API contract principles
Current owner-only HTTP operations remain under /api/host/control: catalog, openapi.json, integration-targets, interpret, plan, execute, plans/{planId}. The v0.2 proposed read projections are semantic capability search (bounded, cursor-based; action and research scopes separate), capability detail, per-grant account/binding discovery, source resources and authorized change streams. Add only after the corresponding source port exists. Scope cursors to principal, filters, grant revision and catalog snapshot; stale cursor returns explicit resync. Stable keyset ordering, bounded response sizes, no shared private cache. Generate OpenAPI, MCP and eventual SDK descriptions from the same approved contract. Do not create alternate execution paths.
Plan: accept only validated typed intent, existing action IDs and explicitly resolved target/account; a future rich typed input must extend the canonical planner rather than tunnel arbitrary JSON through string args. Plan digest binds canonical operation/version, input, resolved account, destination, exact payload and revision, effects and policy. Execute via existing trusted approval/claim boundary with fresh grant and source checks. Scope idempotency to actor/operation/digest and existing claim, not an invented second journal. Read-only planning can already perform a bounded authorized read: do not label all plan calls side-effect-free. MCP tools/call must not give an agent the desktop owner token or approve its own mutations; externally exposed calls should use separately scoped existing or explicitly designed client grants; unimplemented grant classes fail closed. For current v0.1, no new external authority.
Errors: typed safe code, correlation, status, retryability, optional bounded details. Distinguish unsupported, unavailable, denied, needs clarification, stale, pending approval, completed, uncertain. Uncertain effects reconcile original receipt, never automatically resend. Typed result schemas should be extracted from actual executors; unknown results stay unverified rather than invented. No fake compliance claim.

## 4. Resource, sync and event contracts
Adapt existing stream envelope rather than another model. Preserve stable account + stream + unit identity, provider/native revision, payloadRef, observation time, content digest, permission and provenance. Common resource families: conversation/message, contact, document/file, task, calendar item, repository/issue, media, order, account/transaction, device/state. Model-specific operations and field support must be discoverable; no lossy forced equivalence (chat thread != email thread, booking != order). Deletion requires affirmative evidence or a complete authoritative snapshot; missing/partial/stale does not mean deleted. Preserve namespaced extensions and private raw evidence only under grant.
Separate page cursor from durable ingestion checkpoint; checkpoint advances after durable accepted records/deduplication, not before. Use existing Rust HQKG/index/journal where appropriate; source payload and Host grants remain with existing owners. Evidence streams are budgeted and local-first. Browser observations need not represent complete provider state. Event projections can map to CloudEvents source, id, type, subject, time, specversion, data; source+id dedupe, opaque resource refs, no payload leakage. Consumers reconnect using authorized revision cursor; event replay never executes a mutation. No webhook receiver or scheduler until supported by existing authorized transport and product need.

## 5. Composition and learning
VLANG/VEC resolves human text to typed operations and existing approved program recipes; native DAG validation checks schema compatibility, acyclicity, bounded compute, provenance and policy. Existing owners perform effects; a DAG never becomes a grant. Each step has effect class, input/output bindings, expected revisions and failure/compensation semantics. Independent reads may run concurrently; effect steps serialize where needed. Do not claim distributed transaction or automatic compensation; uncertain external steps stop dependents and require reconciliation. Teaching a phrase or discovering a UI template does not authorize future changes. TierFlow generates views and forms from typed schemas, plus trusted exact approval presentation; never grants or executes from rendering. Reuse accepted recipes and deterministic computations to avoid repeated LLM inference.

## 6. Priority implementation increments (not a separate tracker)
A. Harden current universal-api.mjs: bounded filtered discovery for inventory and existing action projections, source/version references, truthful schemas and contract tests, retain current URLs; no new auth. Distinguish UTF-16 planner length from JSON Schema code points and enum trim; document existing browser session/CSRF vs owner-token surface accurately. Validate response types based on source. Use existing tests/control-http paths and dependency packaging.
B. Bind HQ semantic registry and Studio atom descriptors in a derived crosswalk; keep candidate mapping noncallable. No raw primitives surfaced.
C. Reuse existing account/session and source grant owners; implement one actual account-bound read for a supported existing source (select only after source inspection), verify account mismatch, revoked grant, stale source and partial data. First external write only if Host risk enforcement, exact recipient/payload and provider evidence support it; current planner refuses wired R3, so do not lower risk or bypass this limitation.
D. Connect actual stream observations to existing Host stores/HQKG; incremental readback, checkpoint, dedup, tombstone and restart tests.
E. Expose least-privilege MCP projection of proven reads plus non-effecting proposals where allowed; test client cannot self-approve, access other accounts or use internal primitives. No direct provider API dependency.
F. Extend reusable programs and native DAG with already-authorized typed operations; live PWA/TierFlow readback. Broaden family by family, not a thousand bespoke handlers.
Acceptance: source closure + real HTTP or native invocation + explicit authority check + persistent receipt/readback as applicable + negative/revocation/restart cases. Candidate counts, mapped counts, wired counts, live-tested counts and account-granted counts remain separate. Tests not executed in this design round. No product source modifications.
