## First actual integration slice
1. Add windows-sys features SystemInformation, Storage_FileSystem to incumbent crate (Foundation/Threading already present). Import resources.rs and serialize its typed result via existing serde_json. Native worker receives only closed Host command enum, not caller-provided shell command. Implement system.resources.read and system.volume.capacity; use approved drive argument and no private paths. Compute CPU percentage between two real observations, first sample has no percentage.
2. Add catalog rows using existing workbook style (id, title, category, owner, executor, readiness, risk, target, surfaces, privacy, args, examples, reversible, subject, priority, precondition). Catalog surfaces supported by current enum are text/desktop/mobile/visual; MCP projection is generated in transport, not an invented catalog surface enum. Map descriptor schemas through incumbent planner and dispatcher. Host uses current session/grant and readback; native result must not contain credential content or authorize anything. Register semantic IDs as proposed, promote through existing process.
3. Add explicit MCP mapping to existing transport. Do not create standalone MCP server. Every registered *public* action must have matching MCP projection and GPUI user-invocation contract; internal worker and privileged admin/authority actions are not public remote capabilities. R0 reads need authenticated grant and scoped results; R2 effects use exact current Host approval plan/receipt; unsupported/disabled actions remain discoverable as such only where allowed, not executable. No duplicate auth or schema registry. Reconcile capability IDs and avoid conflicting with workstation God Mode changes.
4. App uses existing semantic command control and Host result revision; add discoverable controls to existing GPUI, not a second frontend. Same action ID, request schema, grant, effect and evidence on both surfaces. User may naturally ask "show computer memory" and get typed result. MCP first: real ChatGPT tool discovery/invocation, then same action through app and paired viewport, compare result schema and provenance (values may change).
5. Test current source, stage source-pinned release, verify signed/hashed release evidence and supervised handover. First live MCP refresh only if new tool schema requires it. Changing supported configuration does not require re-install. Record actual response and negative tests; do not claim all actions live merely because proposed descriptors exist.

## Common result and observation
Result schema vivim.windows.native-result/1: actionId, status (ok/unsupported/denied/stale/partial/error), observedAt, source, scopeRef, revision, data, evidenceRef, receiptRef when an effect ran. No fabricated successful receipt; no host effect directly from GPUI or MCP. Native signals use source ID, source generation, sequence, approved scope, event kind, bounded payload, observed time and gap marker. Persist checkpoint with successful existing graph transaction; gaps invalidate dependent facts. No raw ETW private payload or whole-system history in Labs.
