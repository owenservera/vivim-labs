# VIVIM UX, Settings & Configuration — ownership R001
2026-11-25 | Workstream owner: ChatGPT settings/configuration session | Status: source-grounded initial research and proposed convergence; not implemented or release-accepted.

## Mandate
Own the full settings experience, typed configuration inventory, navigation, onboarding linkage, effective-value provenance, migration, recovery, and consumer/developer boundary. Coordinate subsystem owners; do not fork their registries, effect authority, stores or renderer. ARBOR main is implementation authority; Labs is design/research authority. Existing Windows-level Settings menu enters the one GPUI surface; PWA is its authenticated viewport. Rust-first. No new provider API or browser driver. No raw secrets, private history, credentials or account IDs in Labs, diagnostics, exports or graph. Settings navigation and product feature operation remain distinct. Owner retains product-scope approval.

## R002 — Founder mandate: system-wide configuration authority (2026-11-25)
**Confirmed scope: all VIVIM use, all existing and future components, not just V1 or UX.** V1 is the first delivery milestone, not the architectural boundary. This workstream owns cross-component configuration semantics, discoverability, lifecycle, migration, effective-value provenance and the user-facing control surface. All subsystem owners must converge on this shared contract; no new independent settings silos, competing preference registries or duplicate UX. Domain stores remain authoritative for their own state; Host remains sole effect/permission authority, and native GPUI the sole product renderer. Centralization is logical, not indiscriminate flattening into one database.
Coverage includes Host/World, GPUI, PWA, Studio/external apps, VLANG/compiler, AutoWiki/knowledge graph, personal intelligence, providers/models, agents/jobs, workspace/files, device/MCP/remote access, integrations, installation/update/recovery, security/privacy, diagnostics, developer tools and every future registered capability. Include operational configuration, not just editable user preferences; expose sensitive or system-only values only through appropriately redacted and scoped views.
Existing components: inventory all keys, defaults, environment variables, CLI flags, persisted stores, overrides and writers; map each to a stable ID and authoritative domain, reconcile conflicts, and migrate incrementally without disrupting working installations. Future components: supply typed descriptors, owner/domain, scope, default and validation, effective-value provenance, sensitivity, apply mode, dependencies and migration/version semantics; reuse existing registration and mutation contracts. No requirement for a new consumer UI control when the setting is internal, derived or immutable. No runtime provider admission gate introduced by this policy.
One shared registry/read model and Host-backed mutation path (or explicitly classified local presentation-only preference) across native desktop, phone viewport, natural language, onboarding, CLI/developer tools and approved automation. Separate desired configuration, observed status, grants, secrets and policy. A configuration change never implicitly grants access; no secret values in registry projections or logs. Track legacy exceptions with owner, reason and convergence plan.
Acceptance: each registered configurable capability has a discoverable typed contract, a single authoritative writer, truthful effective-state readback, durable recovery and appropriate scope; no parallel settings surface or untracked config key. V1 acceptance remains governed by the user journey, while this mandate applies indefinitely beyond release boundaries. Implementation sequencing and exact schema remain proposed until source reconciliation.

### Research principles
- Windows app settings: stable, labeled categories; reserve settings for preferences and infrequent info, keep frequently used actions contextual. https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings
- Windows settings supports natural-language discovery; VIVIM can implement deterministic semantic aliases through its existing VLANG capability registry. https://support.microsoft.com/en-us/windows/experience/exploring-windows-settings
- Apple HIG: defer genuine systemwide options to operating system; don't replicate global controls misleadingly. https://developer.apple.com/design/human-interface-guidelines/settings
- NN/g progressive disclosure: keep primary choices prominent, reveal technical options as needed. https://www.nngroup.com/videos/progressive-disclosure/
- OWASP secure-by-default, least privilege, scoped secrets, redact logs; use OS-protected secret references, not a general config file. https://devguide.owasp.org/en/04-design/02-web-app-checklist/01-secure-by-default/ ; https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html ; https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html

## Era II — One Settings Center
Proposed information architecture: My AI & connected accounts; Personal knowledge & sync; Workspace & storage; Devices & remote access; Privacy & permissions; Experience & accessibility; Models & resource usage; Automations & agents; External apps & integrations; Backup, updates & recovery; Developer & diagnostics. About belongs under Help with a link. Visible rows derive from registered descriptors and actual capability status. Unknown/unimplemented options remain documented in Labs, not fake controls. Each category provides user-language summary, current state, actions and advanced disclosure. Search supports stable setting IDs and aliases (e.g. 'stop syncing YouTube', 'change my main AI', 'disconnect phone'); preview before sensitive changes. Every row should show effective value and reason when overridden, disabled or awaiting connection. Settings available from menu, natural language and contextual deep links; no independent mobile settings renderer.

Separate six kinds of state: user preference, workspace configuration, authorization/grant, observed runtime status, secret reference and policy/constraint. A connected account is observed state; permission to acquire its history is a grant; preferred provider is a preference. Never model them as one checkbox. Use existing domain stores behind a canonical read projection and Host-owned mutation contract, not a second master database. Presentation-only settings may remain local, explicitly scoped and never confer access.

### Proposed typed settings contract
Descriptor: stable id; schema version; title/description; aliases; category; value type and range/enum; default; scope (owner/workspace/device/session); owner domain; mutability; sensitivity; apply mode (immediate/restart/reconnect/approval); dependencies; V1 availability; control kind; legacy mapping; source. Effective read: desired/effective value, provenance (default, stored, environment, CLI, policy), revision, availability, observed time, reason, pending action. Mutation: request_id, expected_revision, setting_id, scope_ref, typed value, optional authorization_ref. Host validates type, scope, dependency, policy and consent; receipt reports applied/pending/rejected/conflict, before/after redacted values, revision and recovery hint. Idempotent request IDs; reconcile uncertain outcome instead of duplicate execution. Do not return secrets in any projection. Durable change history should be local and redacted. Single writer per domain, atomic replacement or transaction, readback, migrations and recoverable prior version. Legacy env/CLI overrides stay explicit; no override can grant permission or change verified account identity. No policy relaxation via UI.
Use semantic graph and VLANG for discovery and navigation, not secret indexing or authority. Generate UI descriptors from native typed source and existing capability metadata; avoid runtime duplicated schemas. No provider tokens in graph.
