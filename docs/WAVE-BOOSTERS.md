# Labs boosters alongside VIVIM platform waves

**Purpose:** concrete independent, process-heavy Labs work for each wave. **Not** a substitute for A–H source implementation or permission to edit TierFlow/Harness/HQ lane-owned files. The central full 12-factory program remains [Engineering Evidence Factory](ENGINEERING-EVIDENCE-FACTORY.md) and continues *through every wave*, not just as occasional extras.

## The parallel model

**Core wave**: canonical source + reviewed architecture + Integration N acceptance. **Labs booster**: high-volume, source-pinned discovery, test matrices, compatibility, tooling, evidence, catalogues, assets and process improvement. Labs may start independent read-only/fixture work ahead of dependent code. It retests each accepted candidate on actual canonical repo commits. Labs' test results cannot themselves grant canonical source, Host or KB write authority.

## Always-on responsibilities across ALL stages

1. **Git/process operations:** safe fetch/fast-forward where eligible, status of dirty/active worktrees, source SHAs, write-path conflicts, integration report and evidence linking; no unapproved main promotion.
2. **Test operations:** run native applicable test commands, independent clean builds, error/failure reproduction and trend monitoring with real exit codes, not summary-only model claims.
3. **Catalogue federation:** continuously find references to canonical catalogues while maintaining their separate owners.
4. **Asset inventory:** propose, specify, test and link reusable components, fixtures, templates, recipes, adapters, agents/skills.
5. **Agentic excellence:** document ZCode/HQ tools, models, skills, agent recipes, quality and throughput, with independent evaluation and no redundant orchestrator.
6. **Security/privacy:** adversarial inputs and denied/uncertain/revoked actor/device states; no synthetic proof inflated to live permission.
7. **Evidence graph:** link capability/implementation/contract/consumer/test/evidence/platform to Repos HQ canonical identity, **without becoming second knowledge authority**.
8. **Production preparedness:** continually investigate clean builds, dependencies, release profiles, migration and rollback, but only the owner grants live changes.

## Booster artifact guidance (local designs actual workflow)

For each booster work item, record at least the source commits, corpus/test identity and provenance, a reproducible command/fixture when relevant, observations and failure reasons, maturity stage (**discovered → specified → unit verified → integrated → environment verified → production verified**), and target canonical owner. Avoid inventing fixed fleet/task schemas before inspecting ZCode/HQ.

## Boundaries, priority and sequencing

Labs can pursue W4–6 readiness research while W3 source implementation is active, provided no forbidden dependent action is taken. W4–6 **acceptance** still follows Integration N gates and true native/device evidence. Cross-repo production paths, live Host/KB/Studio/Android, providers and merger authority remain with their approved owners.

**First parallel booster focus with Wave 3:** quality-controlled natural-language corpus, discovery of candidate catalogues/assets, A/B/D differential compatibility, real A–H security and SQLite reliability regressions, repeatable clean builds, and an initial capability evidence map. Proposed 10k NL / 1k candidates / 500 assets / 2k adversarial numbers are initial targets; **volume never proves correctness**.
