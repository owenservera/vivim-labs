## ERA 1 — Sequencing and unambiguous release meaning

**Pre-G:** four isolated evidence/portable-proof waves (PG-00 through PG-03). They may inspect, model, compare, test synthetic fixtures and prepare strict owner handoffs **only under their separately approved isolated paths**. No edits to frozen A–F, integration G, root workspace, original Host, existing source intake or main. These pre-G waves are optional and **must not block or delay G**.

**G:** execute the *existing* sole integrator's Proposal 5 source-convergence work order. Six A–F freeze reports plus a current exact architecture base and real root manifest plan. Do not treat this foundation document as a rival G runbook.

**Post-G:** W2-F0 security and actual coherent internal source/build is the first required dependency. Later W2-F1/W3-F2/W3-F3/W3-F4/W4-F5 are **candidate owner-reviewed** capabilities. Keep optional future-proofing out of the original beta critical path unless G explicitly admits it after real source/runtime proof.

**Release:** W5-F6 independent negative/device tests, W6-F7 staged PWA-first Windows beta and explicit owner real-data cutover. FB-01 optional advanced functionality later. Neither an isolated source commit nor a V8 synthetic assertion counts as real product acceptance.

### Hard non-goals through the baseline beta

- No replacement Host effects catalog/planner/dispatcher, UI publisher, source wiki writer, HQKG graph, journal or durable scheduler.
- No external donor repo runtime path, cloud fallback, provider API, new Playwright/Puppeteer runtime or private source corpus added to public HQ/Labs.
- No unrestricted native plugin/JS eval, model-authored effect handler, comment-defined grant, or AI autonomous personal memory write.
- No native APK build/sign/publish milestone for the initial PWA-first beta; remove the stale required APK resource only via G/A scoped source integration.
- No pretending that a source-defined feature, file, fixture, screenshot or V8 proof is actual secure and device-accepted product code.

## ERA 3 — Future prompt generation and test/acceptance model

Use [PROMPT-FACTORY-SCAFFOLD.md](./PROMPT-FACTORY-SCAFFOLD.md) to generate later dedicated worker prompts from this wave manifest. **This round deliberately does not publish executable multi-worker prompts**: the current G input has not been merged, so inventing target SHA/path or runnable build commands would cause stale branches and duplicate owners.

### Acceptance must be narrower than marketing language

1. **Source verified:** immutable repo SHA/path/blob, license and transitive import closure; code is present, not necessarily runnable.
2. **Unit verified:** Node/Bun/Cargo test actually ran with exact executed command/exit code and real module imports, not only synthetic V8 assertions.
3. **Runtime verified:** owner-bound actual Host/HQ/Rust/TierFlow path; catalog/world/source/actor revisions checked, result and real receipt observed.
4. **Device accepted:** installed Windows Tauri and physical HTTPS browser PWA, pairing, revocation, offline shell and signed-in Chrome provider journey tested.
5. **Release accepted:** red-team, per-volume storage, no-donor build, source secrecy, backups/rollback and owner-go before actual personal data cutover.

### Evidence and risk rules for every generated worker

Every future lane prompt MUST require: base Git SHA; exact owner allowed paths; all used source pins; no editing frozen workers/G/main; real versus UNRUN test ledger; no live user-data ingestion; no owner token or external browser credential; no duplicated authority; bytewise source status; negative tests for stale/dangerous inputs; explicit integration handoff. Worker branch remains isolated unless a sole G integration owner accepts it.

### Dependency / product split

**P0 first:** root builds, no-donor closure, native trusted Host launch, PWA device request-bound auth, Host effect journal single writer, HQ source scope, measured protected storage baseline. These are present as source or blocker records, **not fixed by architectural drafting**.

**Product-levelling foundation:** one source-attested semantic wiki IR, native generational pure compute, versioned actor/input/graph trace, Host-owned language admission, PWA reversible view, trusted DCB/memory reads, and explicit capability activation/rollback. These require actual implementation and real cross-language tests.

**Stretch:** broad learned prediction, auto-adaptive meta-coding v3, app builder as truly deployable apps, complete user-corpus import, plugin marketplace, autonomous mission and native APK. They remain proposals until owner-reviewed and proven.
