## Ranking methodology (estimated, not benchmarked)

Candidate score = **7×W + 4×F + 3×R + 2×M** (max 80): 
- **W (1–5):** likely batch/CPU/memory complexity and data volume; 5 = large parsing/replay/traversal.
- **F (1–5):** likely frequency or latency sensitivity; 5 = per-message/per-update hot path.
- **R (1–5):** cross-surface leverage (HQ/Host/Studio/phone) and deterministic reuse.
- **M (1–5):** portability to a bounded, testable **pure** Rust function, not implementation ease or delivery approval.

Ties resolve by W, F, R, then inventory encounter order. Scores are screening heuristics, **not measured performance** or forecasts. `CORE` = high-potential shared pure native computation; `ACCEL` = selective native read/compute adapter while the current JS/TS authority, I/O or interface stays in place. A high score creates a profiling and parity priority, **not a migration mandate**.

## Execution cadence and behavior-based frequency (added 2026-11-12)

**Separate dimensions:** The existing **F** score is an estimated *latency sensitivity / opportunity signal*, **not an observed invocation count**. The new **Cadence** column describes the **likely activation pattern**, while **User H/M/L** and **Dev/admin H/M/L** describe estimated *activity intensity under corresponding behaviors*. They are not measurements, workload shares or requirements to run something continuously.

- **ALWAYS_ON:** actually continuous/polling/daemon workload while the relevant service is active. **No candidate in this first-pass list is verified always-on**; a possible background loop is not classified ALWAYS_ON until caller/scheduler evidence demonstrates this.
- **HIGH_FREQUENCY:** potentially every frame/message/chunk/keystroke or hot-path iteration **during active use**; not necessarily active 24/7.
- **FREQUENT:** repeated event-triggered processing (e.g., a journal receipt or evidence update) with many events in active sessions.
- **USER_DEFINED:** invocation rate strongly depends on user behavior. **H** = active chat/edit/search/automation sessions, **M** = periodic import/inspection/knowledge use, **L** = occasional explicit user request. The band expresses plausible *peak behavioral intensity*, not guaranteed usage; even H can be zero when idle.
- **MEDIUM_FREQUENCY:** periodic incremental or moderately batched work tied to refreshes, rebuilds, or state changes.
- **LOW_FREQUENCY:** explicit full inventory, incident, maintenance or batch operations that are rare but may be computationally expensive per call.
- **DEV_ADMIN:** primarily development, indexing, workspace management, profiling or admin work. **H** = on each source update/query/active dev loop, **M** = occasional sessions, **L** = infrequent maintenance. Does **not** mean a developer process is always running.

The two H/M/L fields are **separate**: a dash means not this candidate's dominant triggering audience, not impossible usage. **Primary activation** is a testable hypothesis, not an audited caller. Categorization is provisional based on module responsibility and source names, without runtime frequency instrumentation. Measure invocation counts and duty cycles before any automated scheduler, pre-warming, Rust migration or power budget decision.

**Current estimated distribution:** ALWAYS ON 0; HIGH FREQUENCY 14; FREQUENT 11; USER DEFINED 36; MEDIUM FREQUENCY 6; LOW FREQUENCY 3; DEV ADMIN 30. The zero ALWAYS_ON result is deliberate: verified continuously running activity was not established in this audit. The detailed mapping includes one primary cadence per candidate, although actual usage may involve multiple triggers.

**How to prioritize:** use two axes rather than conflating scores: **time-weighted total cost** = measured call rate × CPU/runtime and memory-duration, and **peak cost** = p95/p99 CPU, allocation and peak RSS for individual expensive bursts. For idle/power budgets inspect true ALWAYS_ON duty cycles first; for user-perceived latency inspect HIGH_FREQUENCY and USER_DEFINED/H; for operations inspect DEV_ADMIN/H and rare batch peak pressure. Do not normalize estimated H/M/L to exact calls per second.

## How to use this list

**First shortlist** = rank 1–20 for benchmark/contract inspection, not blind bulk porting. Separate already-present HQKG algorithms from truly missing capabilities, measure actual CPU time/p95/heap/bytes/s, and only then choose native targets. **Next wave** = 21–50 for standardized adapters and shared contracts. **Later** = 51–100 or remain JS/TS when native crossing, WebAssembly/PWA packaging or feature risk exceeds benefit.

**No authority transfer.** Host retains permissions, consent, World writes, browser effects and receipts; Studio owns signed-in browser capture/sender, HQ owns dev index/SQLite transactions and Wiki publishing, TierFlow owns UI rendering, phone remains PWA-first. Pure native engines accept authenticated typed input; they do not authenticate themselves. No duplicate graph, store, scheduler, effect executor, browser controller or provider API. Domain-specific private source material must not be copied into development HQ.

**Optimization choices:** Native shared library for repeated CPU-heavy transforms; in-process Rust ABI when available; bounded child/IPC for desktop-only computation; web/WASM only after measuring size/latency/security tradeoffs. Retain mature JS/TS paths when native gives no proven benefit. Cache ownership and invalidation are separate gates; byte zero-copy promises need proof.

**Evidence and promotion:** Each target requires source entrypoint + caller path, representative synthetic fixture, baseline wall-clock/p95/heap, Rust parity, stale/rename/delete/revoke cases as applicable, regression exit receipts, cold-start/size/energy cost, fallback and rollback. For personal workflows also verify disclosure, Host grant and device evidence. Rust core compile and no-donor package tests are mandatory before claiming integrated or faster. No actual VIVIM/ARBOR/Labs migration comparison was run here.
