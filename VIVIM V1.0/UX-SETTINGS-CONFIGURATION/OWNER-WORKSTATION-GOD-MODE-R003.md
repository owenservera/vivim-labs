## R004 — Owner directive: live workspace membership, no per-folder deployment

The current God Mode connector must let authorized ChatGPT sessions add and remove development folders on demand. A folder registration is ordinary runtime configuration, not a new binary release, plugin, tool schema or per-session installation. Host remains the single authoritative writer; integrate the existing Settings configuration domain and existing native file/terminal ports rather than introduce a separate store or renderer.

P0 implementation contract (proposed, not live): locally owner-approved standing development workspace scope; stable root IDs and revisioned membership; list/add/remove through the existing authenticated Host/MCP control path; validate canonical paths and exclude protected authority/credential locations and reparse escapes. Adding a folder already within the approved scope needs no separate local approval or build. Outside the standing scope requires the supported owner authorization path. Removal stops new managed operations on that root, reports running jobs and invalidates stale bindings; it must not delete files or be represented as OS sandbox confinement. Persist and read back the new revision; all authorized sessions see the same effective membership; no metadata refresh for ordinary membership changes. Existing terminal scope and Host-owned receipts remain intact. Tool list changes require discovery only once when the new operations are introduced. No Studio/Harness changes (R033 hold).

Acceptance: two ChatGPT sessions share the same revision; add a real approved development repo, list/read and execute a harmless command there, remove its registration, verify subsequent managed operations are denied, preserve files and unrelated sessions, restart/reconnect and verify persisted membership. Test stale revision, duplicate ID, protected path, unauthorized boundary, and concurrent modifications. No rebuild/restart/refresh per folder. Priority above further static-profile expansion. The current staged batch still uses the old fixed-root contract and does not satisfy this requirement.

## R005 — God Mode machine-wide operating scope: source audit and implementation direction

Owner clarification: God Mode is the current private workstation connector, not a collection of registered project roots. Workspace add/remove (R004) is useful organization, not the authorization model for God Mode. User Mode remains deferred. Goal: one explicit local owner authorization for general terminal, native filesystem and application operations within the Windows identity's actual machine access. Do not equate this with SYSTEM, administrator elevation, credential extraction, circumvention of Windows protections or unrestricted third-party effects.

Source inspection pinned to ARBOR 488ab7365a9c902e06e6346ed878b2bb0a7dcf60:
- MCP workstation-tunnel.cjs requires registered program and root IDs, relative file paths, pinned grant/config digests and an expiring grant. Terminal request 5997 UTF-8 bytes at MCP.
- Host workstation-terminal-request.mjs accepts only program ID and relative cwd; workstation-terminal-policy.mjs validates up to 64 programs, 16 roots, pinned binary digests, 30-minute command limit, and a local policy expiration of at most 24h. Existing installed profile uses 8h. A starting cwd is explicitly not an OS sandbox for a general CLI.
- Host workstation-file-port.mjs and native vivim-workstation-files.rs resolve registered roots, refuse reparse traversal, support bounded UTF-8 operations (65536-byte native limit), and protect specific sensitive file names. No absolute-path/native whole-volume contract.
- Native workstation_process.rs already launches canonical executable + cwd + argv and explicit environment; workstation_windows_job.rs uses Windows CreateProcessW, creation-time Job Object containment, inherited standard handles only and CREATE_NO_WINDOW. Current worker is not an OS sandbox, interactive desktop app controller or full ConPTY terminal. Session worker: eight running jobs, 64 retained, 30-minute timeout, 64KiB per-stream tail.
- Existing install couples grant, root/policy config and runtime seals; changing a root or program can require handover. No live owner-approved machine-scope authority/renewal route currently.

P0 architecture (proposal, not deployed):
1. Add explicitly locally enabled owner-machine profile to incumbent Host and MCP, preserving legacy contracts and private tunnel identity. Standing owner authorization controls machine scope and local revoke; short-lived authenticated leases may renew via trusted Host, never a remote self-grant. Separate authorization state from binary release and workspace organization. Preserve receipts, no automatic replay, authenticated access and protected authority/secrets.
2. Under that profile support absolute local paths, accessible fixed volumes, canonical executable resolution by PATH or explicit path, arbitrary argv and absolute cwd through existing native worker. Bind resolved identity and request at admission; no per-binary permanent registration for routine execution. Enforce Windows account ACLs and UAC; no forced elevation, secret readout or authorization-store mutation by remote tools. Workspace membership is optional metadata.
3. Extend native file APIs for explicit absolute local paths and drive inventory, paginated/binary streaming, search, rename/copy/move and digest-bound mutations. Preserve sensitive-data protections and explicit consequential-operation semantics; do not expose credentials. Distinguish reparse target identity, OS access denial and missing path. Do not remove existing safety limits indiscriminately.
4. Improve existing worker for ConPTY, long-lived process sessions, streaming/spooled output and resource-aware concurrency; separate intentional GUI application launch/lifecycle from owned terminal Job Object lifetime. Actual external application interaction belongs to dedicated Studio/Harness convergence session (R033), not a second browser surface.
5. One source-pinned production upgrade, with local owner authorization, maintenance/drain/rollback and existing tunnel supervisor preserved. Thereafter normal app/path changes need no rebuild, metadata refresh or separate registration. Central settings reflect effective profile, permissions, lease/revocation, filesystem, terminal and launch status via existing Host; no competing settings store.
6. Acceptance: real authorized non-workspace local directory and another available fixed volume if present, ordinary file read/write round trip with owned fixture and safe cleanup, installed unregistered executable version, stock Craft CLI version/doctor without fork, cross-session output/reconnect, revocation and rollback. No actual credential, private account, protected OS or unrelated files accessed; OS-denied operation stays denied. Verify actual GUI capability separately, not infer from terminal.
